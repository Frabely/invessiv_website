## Ziel

Nach 29.1 setzt jeder Produktivpfad `customers.customer_number` selbst; der Spalten-Default
`nextval('customers_customer_number_seq')` und die Sequenz sind nur noch Altlast. Diese Einheit entfernt beides, stellt
alle Tests, Fixtures, Seeds und Smokes auf explizite Nummern um und räumt die Regeln auf.

**Warum getrennt von 29.1:** `DROP DEFAULT` vor dem Deploy des neuen Codes hätte jede Kundenanlage am `NOT NULL`
scheitern lassen; außerdem bliebe 29.1 ohne Default nicht mehr per reinem Code-Revert rückrollbar
(`../AGENTS.md`: Entfernen erst in einem späteren, eigenständig sicheren Release).

## Schritt 3 — Migration und Modell

Migrationsnummer beim Schreiben ermitteln (höchste bestehende + 1), nicht aus diesem Plan übernehmen. Eine Datei, zwei
Statements:

```sql
-- Since folder 29 the write path sets the customer number; the sequence is no longer read.
ALTER TABLE customers ALTER COLUMN customer_number DROP DEFAULT;
--> statement-breakpoint
DROP SEQUENCE IF EXISTS customers_customer_number_seq;
```

- Beide Statements sind wiederholbar (`DROP DEFAULT` auf eine Spalte ohne Default ist folgenlos, `IF EXISTS`).
- Das ist eine **dokumentierte Ausnahme** von „Migrationen sind additiv“ und wird in `packages/db/AGENTS.md` im
  Abschnitt „Migrationen“ mit Begründung eingetragen (wie `0024`): kein Leser mehr seit 29.1, Rückweg siehe unten.
- `packages/db/src/record-configuration/crm/customers.ts`: `.default(sql\`nextval(...)\`)`entfernen; Spalte bleibt`integer(...).notNull()`. Migration und Modell sind deckungsgleich (Review-Punkt).
- Unique-Indizes `customers_customer_number_uidx` und `customers_id_customer_number_uidx` bleiben unverändert.

## Betrieb — K0009 auf K0002 (eigener Schritt, unabhängig von 29.2)

Möglich, sobald 29.1 in Produktion läuft; eine Sequenz muss dafür nicht mehr neu gestartet werden. Muss vor der nächsten
Kundenanlage passieren, sonst erhält ein neuer Kunde den Vorschlag K0002.

```sql
BEGIN;
SET LOCAL lock_timeout = '5s';
LOCK TABLE customers IN SHARE ROW EXCLUSIVE MODE;
SELECT id, customer_number, version FROM customers ORDER BY customer_number; -- erwartet: 1 und 9, 2 frei
UPDATE customers
SET customer_number = 2, version = version + 1, updated_at = now()
WHERE id = '<UUID von K0009>' AND customer_number = 9 AND version = <gelesene Version>;
-- muss "UPDATE 1" melden, sonst ROLLBACK
COMMIT;
```

Vorher klären, ob K0009 schon extern verwendet wurde (Angebot, Rechnung, E-Mail).

## Rollback

- Vor dem Prod-Deploy: Revert des PRs genügt.
- Nach `db:migrate:prod`: Der App-Code braucht weder Default noch Sequenz, ein Rollback der App ist ohne DB-Eingriff
  möglich. Soll der alte Sequenzweg zurück, neue Migration:
  `CREATE SEQUENCE customers_customer_number_seq AS INTEGER START WITH <höchste Nummer + 1> MINVALUE 1;` und
  `ALTER TABLE customers ALTER COLUMN customer_number SET DEFAULT nextval('customers_customer_number_seq');` —
  Startwert aus dem Bestand bestimmen, nicht aus dem in Schritt 0 notierten Wert.
